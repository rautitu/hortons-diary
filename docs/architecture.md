## System boundary

Build a modular monolith. One Go process owns HTTP routing, server-rendered
pages, HTMX fragment responses, authentication, attack records and later
reporting. PostgreSQL is a separate runtime service, but not a separate
application or microservice.

The browser receives normal HTML pages. HTMX may progressively enhance small
interactions, but every essential workflow must remain usable with ordinary
HTTP form submissions. This keeps the accessibility and failure model simple.

Local and initial production Docker Compose will contain `app` and `db`
services. The initial deployment uses a controlled Linux/Docker host and an
existing Caddy reverse proxy. PostgreSQL stays internal to the Compose network
and stores data on a persistent volume.

## Recommended baseline for phase 2

- **Go:** pin the latest supported Go 1.27 patch release in `go.mod`, CI and
  container builds. Go 1.27.0 was the current stable release when this
  blueprint was written. Do not use an unpinned `latest` image.
- **Router:** `github.com/go-chi/chi/v5`. It stays close to `net/http`, supports
  composable middleware and route groups, and does not impose a framework
  architecture. Standard-library routing is viable, but chi makes auth and
  ownership-scoped route groups clearer.
- **Templates:** standard-library `html/template`, organized as parsed page and
  partial sets. Its contextual escaping is security-relevant and it avoids a
  generation tool in the initial stack. Reconsider Templ only if compile-time
  component ergonomics prove valuable after real screens exist.
- **Database:** `github.com/jackc/pgx/v5` via `pgxpool`, with SQL queries owned in
  `.sql` files and Go types generated by `sqlc`. Keep transactions at the
  application/repository boundary rather than hiding them in generated code.
- **Migrations:** `github.com/pressly/goose/v3`, using versioned SQL migrations.
  It supports explicit up/down sections and can run as a pinned development or
  deployment command. Production migration timing and rollback policy remain
  a deployment decision.
- **CSS:** hand-written, mobile-first CSS using semantic custom properties.
  Ship a single dark theme initially. Avoid a Node/Tailwind build chain until
  the UI is large enough to justify it. Vendored HTMX should be served locally
  with a pinned version and integrity traceability rather than loaded from a
  third-party CDN.

Dependencies must be pinned through `go.mod`/`go.sum` or checked-in static
assets. Phase 2 should record exact versions after verifying their then-current
supported releases.

## Target directory structure

```text
cmd/server/              application entry point
internal/config/         environment parsing and validation
internal/httpserver/     server lifecycle, router and middleware wiring
internal/auth/           authentication and session module
internal/attacks/        attack domain, handlers and application operations
internal/platform/db/    pool, transaction helpers and generated queries
internal/platform/web/   rendering, common view data and HTTP errors
db/migrations/           ordered Goose SQL migrations
db/queries/              sqlc input queries
internal/platform/dbgen/ sqlc-generated code (do not edit manually)
web/templates/           layouts, pages and HTMX partials
web/static/css/          semantic dark-mode CSS
web/static/js/           pinned HTMX and narrowly scoped JavaScript
docs/adr/                architecture decision records
```

`go:embed` should package templates and static assets into the server binary in
production. Development may use the same embedded path initially; live reload
is an optional developer convenience, not an architectural dependency.

## Configuration contract

Configuration comes from environment variables. Commit a `.env.example` with
non-secret placeholders, never a real `.env`. Recommended initial contract:

| Variable | Required | Purpose |
| --- | --- | --- |
| `APP_ENV` | yes | Explicit `development`, `test` or `production` mode |
| `HTTP_ADDR` | no | Listen address; safe local default such as `:8080` |
| `DATABASE_URL` | yes | PostgreSQL connection string; treat as a secret |
| `SESSION_SECRET` | production | High-entropy key used by the accepted local session design |
| `SESSION_COOKIE_SECURE` | no | Must default to true in production and only be false for local HTTP |
| `TRUSTED_PROXY_CIDRS` | production topology | Explicit proxies whose forwarded headers may be trusted |
| `LOG_LEVEL` | no | Logging threshold, with no sensitive request fields |

Fail startup in production when required values are absent, malformed or use
unsafe combinations. Never print secret values in startup errors. A user time
zone is domain data and should not be inferred permanently from a server-wide
environment variable.

## Security and privacy boundaries

Attack records are health-related, sensitive personal data. The following are
non-negotiable implementation boundaries regardless of the eventual auth
provider:

- every read, update and delete query scopes records by authenticated user ID;
  never fetch an attack globally and authorize it only in the UI;
- identity and ownership come from the validated server-side session, never a
  form field, query parameter or HTMX header supplied by the browser;
- state-changing requests require CSRF protection and an origin policy;
- production traffic uses HTTPS, secure cookies and explicitly trusted proxy
  headers; the app must not silently trust arbitrary `X-Forwarded-*` values;
- templates retain contextual auto-escaping; untrusted values must not be cast
  to trusted HTML;
- logs exclude passwords, session tokens, database URLs, form bodies and attack
  details; request IDs and coarse outcome metadata are sufficient;
- database credentials have least privilege, secrets stay outside images and
  version control, and backups are encrypted, access-controlled and tested;
- errors shown to clients do not expose SQL, stack traces, account existence or
  infrastructure details;
- apply request-body limits, server read/write/idle timeouts and later auth rate
  limits; validate all fields on the server even when HTML validation exists;
- define retention, export and deletion behavior before calling the service
  production-ready.

The accepted model uses local email/password credentials, Argon2id password
hashes and opaque server-side sessions stored in PostgreSQL. Registration is
closed: users are invited or created administratively. Password recovery and
email verification remain later scope decisions.

## Initial deployment topology

The host-level Caddy service terminates TLS and reverse-proxies a dedicated
application hostname to the Hortons Diary app. Its configuration is managed
outside this repository. Hortons Diary follows this general topology:

```text
Internet
  -> Caddy :443 (automatic HTTPS, dedicated application hostname)
  -> Hortons Diary app on a private or loopback-only port
  -> PostgreSQL on the private Compose network with a persistent volume
```

The exact hostname, network attachment and app port are environment-specific
deployment configuration and are not recorded in this public repository.
PostgreSQL must not publish a host or public port.

## Confirmed decisions

Tuomas confirmed on 2026-08-25:

1. local email/password authentication with Argon2id hashes and opaque,
   PostgreSQL-backed server-side sessions;
2. closed registration with invited or administratively created users;
3. deployment on a controlled Linux/Docker host, behind a Caddy HTTPS reverse
   proxy, with PostgreSQL in its own container and on a persistent volume.
